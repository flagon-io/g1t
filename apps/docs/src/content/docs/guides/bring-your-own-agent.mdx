g1t is where your coding agents do their work. Claude Code, Codex, Cursor,
OpenCode and any other harness connect to g1t the same way a person's tools
do, and act with the access you give them:

| To | Use |
| --- | --- |
| Read and change anything on g1t from inside the agent | The MCP server at `https://mcp.g1t.sh`: [MCP tools](/reference/mcp/) |
| Push code | git over HTTPS, with an [access token](/guides/authentication/#access-tokens) |
| Start the agent when something happens | [Webhooks](/guides/webhooks/), or a [workflow](/guides/actions/) on `issues` or `issue_comment` |
| Show people how a change was made | The pull request's [session](/guides/why-blame/#sessions) |
| Pass what one agent learned to the next | [Memory](/guides/memory/) |
| Script anything else | The [REST API](/reference/api/), which has the same operations as the tools |

The agent runs where you run it: on your machine, in your CI, or on a
[runner](/guides/self-hosted-runners/) of your own. g1t keeps the code,
the issues and pull requests, the checks and the record of what happened.

## Connect your coding agent

Choose your agent. Every block on these pages follows the choice, and it is
remembered for your next visit.

Signing in opens g1t in your browser. The page lists what the agent will be
able to do; untick anything you would rather it could not, and approve.
There is no token to copy. An agent that asks for nothing in particular gets
the [Agent preset](/guides/authentication/#presets), which never includes an
admin scope. It shows up in
[Settings → Connected applications](https://g1t.sh/settings/applications),
where you can change what it may do, or sign it out.

The agent also needs to push with git, which asks for a username and a
password: use your g1t username and an
[access token](/guides/authentication/#access-tokens) with `code:write`.

Ask it to list the open issues on a repository, or to work on one, and it
will use g1t's tools. It sees only the tools and actions its access allows.

### What to give an agent

Give an agent the least that lets it do its work:

| Choose | For an agent |
| --- | --- |
| Scopes | The **Agent** preset: reading across g1t, and writing code, issues, pull requests, memory and notifications. Add an admin scope only for a task that needs it. |
| Expires | The shortest that fits the work, such as 30 days. |

A token reaches every workspace and repository you can. To keep an agent
to one workspace, give it that workspace's own
[workspace token](/guides/workspaces/#workspace-access-tokens) instead.

The same choices are on the sign-in page for an agent that connects with
OAuth, and in [Settings → Access tokens](https://g1t.sh/settings/tokens)
for a token. A call the agent's access does not allow is refused with the
scope it needs; see [scopes](/guides/authentication/#scopes). Everything
the agent does is done as you, and shows as you in the
[audit log](/guides/audit-log/).

## How an agent works on an issue

1. `issue` with `get`, to read the description, including what done means
   if it says, and to see which pull requests already exist for it.
2. `memory` with `recall`, to read what the project remembers: how to
   build, conventions and traps.
3. `pull_request` with `create` and the issue's number. This opens a draft
   pull request and returns the git remote of its fork.
4. Clone the fork, make changes, commit and push.
5. `pull_request` with `record_session` as it goes, so people can see its
   reasoning.
6. `pull_request` with `get`, to check `overlaps`, `behind` and the checks.
7. `pull_request` with `ready` and a summary of what changed and why.

The call that starts the pull request:

```json
{ "name": "pull_request", "arguments": { "action": "create", "repo": "flagon-io/hello", "issue": 42, "agent": "claude-code" } }
```

`agent` names the harness, so people can see what made the change. Its
commits show with the agent's name and mark too, from the address the
agent writes on them.

Every push runs the repository's [workflows](/guides/actions/#checks) on
the pull request, as for anyone's. `pull_request` with `get` returns its
`statuses` and `required_checks`, the checks the default branch requires
before it merges. When one fails, `workflow` with `get_run` and `job_logs`
says why; push a fix and the workflows run again. Run the same tests and
linters the workflows run before you push, and you will rarely need to.

If merging reports that `main` has moved, pull `main` from the repository
into the fork and push. The pull request can then be merged, or joins the
[merge queue](/guides/merge-queue/) when the repository uses one.

When the merge queue takes an agent's pull request out because it fails
combined with the pull requests ahead of it, g1t
[says which ones and which check failed](/guides/merge-queue/#who-is-told):
in the pull request's session, as an `integration_failure` decision
(`pull_request` `list_decisions`), and as the `integration.failed` event.
The agent reads the other pull request's changes, fixes its own, and
pushes; once the checks pass, the pull request rejoins the queue by
itself. It can say what it changed with `pull_request` `record_decision`
(`kind` `fix`), and `repository` `why` explains any line it is unsure of.

### Repository instructions

Each agent reads a repository's instructions from a file at its root:
Claude Code from `CLAUDE.md`, and Codex, OpenCode and Cursor from
`AGENTS.md`. To keep one file, write `AGENTS.md` and put `@AGENTS.md` in
`CLAUDE.md`. A few lines there make every agent work the same way on g1t:

```md title="AGENTS.md"
## Working on g1t

- Before starting, call g1t's `memory` tool with `recall`. Save anything
  the next agent should know with `remember`, one fact at a time.
- Work in a draft pull request (`pull_request` `create` with the issue),
  and record your session with `record_session` before each push.
- Read `overlaps` and `behind` on `pull_request` `get` before going far.
```

## Record the session

A pull request's session is the record of how it was made: the prompts,
the agent's reasoning, the tools it ran and what they returned. People read
it on the pull request's **Session** tab, and
[why-blame](/guides/why-blame/) uses it to explain each line.

An agent can record its own session with the `pull_request` tool's
`record_session` action. It takes a list of `entries`, each with a `kind`
(`prompt`, `message`, `tool_call`, `tool_result` or `note`) and `text`,
and tool entries also carry the `tool` name. Record before each push: an
entry is tied to the commit that was the head when it was recorded. Do not
put secrets in a session; sessions are as visible as the repository.

### Recording sessions automatically

This is for Claude Code. To have every session recorded without the agent
having to remember, install g1t's hook:

```sh
curl -fsSL https://g1t.sh/install/claude.sh | sh
```

It signs you in through the browser, keeps the token in `~/.g1t`, and adds
a hook to `~/.claude/settings.json`. From then on, whenever Claude Code
works in a g1t pull request's working copy, your prompts, its tool calls
and its closing account are recorded onto that pull request's session as
they happen. It recognises a fork (`g1t.sh/pulls/<id>`) and a branch of a
g1t repository with an open pull request; anywhere else it does nothing.
It needs Node 18 or later, which Claude Code runs on.

To stop recording, remove the `node ~/.g1t/hook.mjs` entries from
`~/.claude/settings.json`.

## Share what agents learn

[Memory](/guides/memory/) holds short notes about a project, or a whole
workspace, that whoever works on it next should know. An agent reads it
with `memory` `recall` before it starts and adds to it with `remember`
when it learns something, such as a test that needs `TZ=UTC`. People see,
pin, edit and forget the same notes on the repository's **Memory** page.
Memory never holds a secret: text that looks like one is refused.

## Staying out of each other's way

Several agents, and people, can work on one repository at once.
`pull_request` with `get` returns:

- `overlaps`: other pull requests in progress that change files this one
  changes, with the paths. An overlap with a pull request for a different
  issue will become a conflict for whichever merges second, so narrow the
  change, or say so in the pull request.
- `behind`: whether `main` has moved since the pull request was made. If
  it has, pull `main` into the fork and push before asking for a merge.

Required checks, [rules](/guides/rules/) and the
[merge queue](/guides/merge-queue/) hold for an agent's pull request
exactly as for a person's.

## Start an agent when something happens

To run your agent without anyone starting it by hand, react to g1t's
events:

- **Webhooks.** Register an address for a repository or a whole workspace
  with the `webhook` tool or in its settings, and choose the events, such
  as `issue.labeled`, `issue.assigned`, `comment.created`,
  `checks.completed` or `workflow.completed`. Each delivery is signed. See
  [webhooks](/guides/webhooks/).
- **Workflows.** A workflow in `.g1t/workflows/` can start on `issues` or
  `issue_comment` and run your agent's command line on a g1t runner, with
  its key in a [secret](/guides/secrets-and-variables/). See
  [GitHub Actions](/guides/actions/).
- **Notifications.** An agent that works as you can read your inbox with
  the `notifications` tool: review requests, mentions, assignments and
  your work's checks, each with why you were told.

## Reviewing as an agent

An agent can review as well as write. Given an issue with several pull
requests, it can call `pull_request` with `changes` and `read_session` on
each, compare them, and read each one's check results from `get`. It can
leave findings on specific lines with `issue` and `comment`, give a verdict
with `pull_request` and `review`, and, with the Write role, `merge` the
best one. It cannot approve or request changes on a pull request it opened.

## Artifacts

Your agent can read and write a workspace's artifacts: its docs, and later
its slides, designs and dashboards. The `artifact` tool does it as you,
so it opens only what you can open, and changes only what you can change.
Its token needs `artifacts:read` to read them (the Read only and Agent
[presets](/guides/authentication/#presets) have it), `artifacts:write` to
make and change them, and `artifacts:admin` to share them or delete them
for good. A token without one of these sees no `artifact` tool, and a
token sees only the actions its scope allows.

1. Find what is there with `list` (narrow with `kind`, `space` or `q`) or
   `search`, which matches words and meaning and returns the passage that
   matched.
2. Read one with `read`. A doc comes back as Markdown in `content`, with
   its top-level `blocks` and their ids, and `can` says whether you may
   edit it or only suggest.
3. Change it with `edit`: `markdown` and a `target`, which is `append`,
   `document` (replace it all), a `section` by its `heading`, or `blocks`
   from one block id to another. With the edit role the change is made, as
   a new version; with the comment role, or with `suggest_only`, it is
   filed as a suggestion that the doc's editors accept or reject.
4. Make one with `create`. Left out `space` and `parent_id`, it lands in
   your Private, where only you can open it until you share it.

```json
{ "action": "edit", "workspace": "acme", "artifact_id": "fol_01kq7c4e6g8j0m2p4r6t8v0x2z",
  "target": { "kind": "section", "heading": "Risks" },
  "markdown": "## Risks\n\nThe migration needs a maintenance window.\n",
  "note": "Adds the migration risk" }
```

Name an artifact by its id (`fol_…`) or by its link. Each action is also
a REST route under `/workspaces/{workspace}/artifacts`; see the
[API reference](/reference/api/). These are not workflow runs' artifacts,
which are the `workflow` tool's. Slides, designs and dashboards answer
that they are not here yet. A workspace's own token cannot use artifacts:
they always belong to a person.

## Filing issues from another system

Anything that holds an access token can open issues: an error tracker, a
monitor, a script. Call the `issue` tool with `create`, or `POST
/repos/{owner}/{name}/issues`, with a title, a description and labels
such as `bug`. Its token needs `issues:write`. The issue is attributed to
the account the token belongs to.

## Tools

Each tool is a kind of thing on g1t and takes an `action`, such as `get`
or `create`. Repositories are given as `owner/name`, and issues and pull
requests as the repository and a `number`.

| Tool | What it covers |
| --- | --- |
| `search` | Code, repositories, issues, pull requests and people across g1t; a tracker's ticket |
| `repository` | Repositories, their settings, rulesets, branches, labels, milestones and releases |
| `issue` | Issues, labels and comments |
| `pull_request` | Pull requests: create, record and read sessions, review, merge, the merge queue |
| `memory` | `recall` and `remember` |
| `workflow` | Workflow runs and logs, checks, deployments, environments and runners |
| `observability` | A project's requests, logs, traces, errors and metrics in production |
| `package` | Packages in every registry |
| `secret` | Secrets and variables |
| `security` | Secret scanning, code scanning, vulnerable dependencies and advisories |
| `webhook` | Webhooks and their deliveries |
| `access` | Who has which role on a repository, and deploy keys |
| `team` | Teams and their members and repositories |
| `workspace` | Workspaces, members, integrations, projects, rulesets and token rules |
| `billing` | Usage, budget and invoices |
| `notifications` | Your inbox |
| `account` | Who the token acts as, and your invitations |
| `artifact` | A workspace's docs |

[MCP tools](/reference/mcp/) lists every action with its required inputs,
its scope and its REST route.

## Other clients

The server speaks MCP over streamable HTTP and answers each request with
JSON. Every call needs to be signed in. Opening
[mcp.g1t.sh](https://mcp.g1t.sh) in a browser shows what the server is, how
to connect, and the tools it offers.

A client that supports MCP authorization needs only the URL. An
unauthenticated request is answered with `401` and a pointer to
`https://mcp.g1t.sh/.well-known/oauth-protected-resource`, from which the
client finds g1t's authorization server, registers itself, and sends you to
your browser. A client that asks for scopes sends them in `scope` on the
authorization request. See
[signing in with OAuth](/guides/authentication/#signing-in-with-oauth).

A client that does not can send `Authorization: Bearer <token>` with an
access token.
