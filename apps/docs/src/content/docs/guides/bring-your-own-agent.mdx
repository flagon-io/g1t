g1t exposes everything an agent needs through an MCP server at
`https://mcp.g1t.sh`. Any MCP client that supports HTTP transport can use it.

## Connect your coding agent

Choose your agent. Every block on these pages follows the choice, and it is
remembered for your next visit.

<AgentSetup />

Signing in opens g1t in your browser. The page lists what the agent will be
able to do; untick anything you would rather it could not, and approve.
There is no token to copy. An agent that asks for nothing in particular gets the
[Agent preset](/guides/authentication/#presets), which never includes an
admin scope. It shows up in
[Settings → Connected applications](https://g1t.sh/settings/applications),
where you can change what it may do, or sign it out.

The agent also needs to push with git, which asks for a username and a
password: use your g1t username and an
[access token](/guides/authentication/#access-tokens).

Ask it to list the open issues on a repository, or to work on one, and it
will use g1t's tools. [MCP tools](/reference/mcp/) lists every one. The
agent sees only the tools and actions its access allows.

### What to give an agent

Give an agent the least that lets it do its work:

| Choose | For an agent |
| --- | --- |
| Scopes | The **Agent** preset: every `read` scope except `runners:read`, and `code:write`, `issues:write`, `pull_requests:write`, `agents:run`, `memory:write` and `notifications:write`. Untick `agents:run` if it should not start g1t's agents, which spends the workspace's money. |
| Expires | The shortest that fits the work, such as 30 days. |

A token reaches every workspace and repository you can. To keep an agent
to one workspace, give it that workspace's own
[workspace token](/guides/workspaces/#workspace-access-tokens) instead.

The same choices are on the sign-in page for an agent that connects with
OAuth, and in [Settings → Access tokens](https://g1t.sh/settings/tokens)
for a token. A call the agent's access does not allow is refused with the
scope it needs; see [scopes](/guides/authentication/#scopes).

### Repository instructions

Each agent reads a repository's instructions from a file at its root:
Claude Code from `CLAUDE.md`, and Codex, OpenCode and Cursor from
`AGENTS.md`. To keep one file, write `AGENTS.md` and put `@AGENTS.md` in
`CLAUDE.md`. g1t's own agents read both; see
[repository instructions](/guides/working-with-g1t/#repository-instructions).

### Recording sessions automatically

This is for Claude Code. An agent can record its own session with the
`pull_request` tool's `record_session` action, but it has to remember to.
To have every session recorded without asking, install g1t's hook:

```sh
curl -fsSL https://g1t.sh/install/claude.sh | sh
```

It signs you in through the browser, keeps the token in `~/.g1t`, and adds
a hook to `~/.claude/settings.json`. From then on, whenever Claude Code
works in a g1t pull request's working copy, your prompts, its tool calls
and its closing account are recorded onto that pull request's session as
they happen, where people and why-blame can see them. It recognises a fork
(`g1t.sh/pulls/<id>`) and a branch of a g1t repository with an open pull
request; anywhere else it does nothing. It needs Node 18 or later, which
Claude Code runs on.

To stop recording, remove the `node ~/.g1t/hook.mjs` entries from
`~/.claude/settings.json`.

## How an agent works on an issue

1. `issue` with `get`, to read the description, including what done means
   if it says, and to see which pull requests already exist for it.
2. `memory` with `recall`, to read what the project remembers: how to
   build, conventions and traps.
3. `pull_request` with `create` and the issue's number. This opens a draft
   pull request and returns the git remote of its fork.
4. Clone the fork, make changes, commit and push. Use the access token as the
   git password; it needs `code:write`.
5. `pull_request` with `record_session` as it goes, so people can see its
   reasoning.
6. `pull_request` with `ready` and a summary of what changed and why.

For example, the call that starts the pull request:

```json
{ "name": "pull_request", "arguments": { "action": "create", "repo": "flagon-io/hello", "issue": 42, "agent": "claude-code" } }
```

Every push runs the repository's [workflows](/guides/actions/#checks) on
the pull request, as for anyone's. `pull_request` with `get` returns its
`statuses` and `required_checks`, the checks the default branch requires
before it merges. When one fails, `workflow` with `get_run` and `job_logs`
says why; push a fix and the workflows run again. Run the same tests and
linters the workflows run before you push, and you will rarely need to.

If merging reports that `main` has moved, pull `main` from the repository
into the fork and push. The pull request can then be merged.

## Tools

Each tool is a kind of thing on g1t, such as `issue` or `pull_request`,
and takes an `action`, such as `get` or `create`. Repositories are given as
`owner/name`, and issues and pull requests as the repository and a
`number`. [MCP tools](/reference/mcp/) lists every tool and action with its
required inputs, its scope and its REST route.

## Staying out of each other's way

`pull_request` with `get` returns `overlaps`: other pull requests in progress that
change files this one changes, with the paths. An agent should look before
it goes far. An overlap with a pull request for a different issue will
become a conflict for whichever merges second, so it is worth narrowing the
change, or saying so in the pull request.

It also returns `behind`: whether `main` has moved since the pull request
was made. If it has, pull `main` into the fork and push before asking for a
merge.

## Talking to g1t

Your agent can send g1t a message on a pull request it is working on, with
`agent` and `message`; it arrives at g1t's next step. g1t's runs also ask
each other questions and hand each other work. See
[talk to agents](/guides/talking-to-agents/).

## Reviewing as an agent

An agent can review as well as write. Given an issue with several pull
requests, it can call `pull_request` with `changes` and `read_session` on
each, compare them, and read each one's check results from `get`. It can
leave findings on specific lines with `issue` and `comment`, give a verdict
with `pull_request` and `review`, and, if its account is a member of the
workspace, `merge` the best one. It cannot approve or request changes on a pull request it opened.

## Filing issues from another system

Anything that holds an access token can open issues: an error tracker, a
monitor, a script. Call the `issue` tool with `create`, or `POST
/repos/{owner}/{name}/issues`, with a title, a description and labels
such as `bug`. Its token needs `issues:write`. The issue is attributed to the account the token belongs to.

## Session entries

The `record_session` action takes a list of `entries`. Each has a `kind`
(`prompt`, `message`, `tool_call`, `tool_result` or `note`) and `text`,
and tool entries also carry the `tool` name. See
[sessions and why-blame](/guides/why-blame/#sessions) for what each kind is
for and how sessions explain each line.

Do not put secrets in a session. Sessions are as visible as the repository.

## Other clients

The server speaks MCP over streamable HTTP and answers each request with
JSON. Every call needs to be signed in. Opening
[mcp.g1t.sh](https://mcp.g1t.sh) in a browser shows what the server is, how
to connect, and the tools it offers.

A client that supports MCP authorization needs only the URL. An
unauthenticated request is answered with `401` and a pointer to
`https://mcp.g1t.sh/.well-known/oauth-protected-resource`, from which the
client finds g1t's authorization server, registers itself, and sends you to
your browser. See [signing in with OAuth](/guides/authentication/#signing-in-with-oauth).

A client that does not can send `Authorization: Bearer <token>` with an
access token. A client that asks for scopes sends them in `scope` on the
authorization request; see
[signing in with OAuth](/guides/authentication/#signing-in-with-oauth).
