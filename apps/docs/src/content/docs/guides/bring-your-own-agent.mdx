Coding agents such as Claude Code and Codex, chat apps such as ChatGPT
and Grok, and open-source MCP clients connect to g1t and act as you,
with the access you give them:

| To                                                    | Use                                                                                                             |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Read and change anything on g1t from inside the agent | The MCP server at `https://mcp.g1t.sh`: [MCP tools](/reference/mcp/)                                            |
| Work from the agent's shell                           | The [g1t CLI](/guides/cli/): `g1t pr create`, `g1t pr checks --watch`, `g1t run logs --failed`                  |
| Push code                                             | git over HTTPS, signed in with `g1t auth setup-git` or an [access token](/guides/authentication/#access-tokens) |
| Start the agent when something happens                | [Webhooks](/guides/webhooks/), or a [workflow](/guides/actions/) on `work_item` or `work_item_comment`          |
| Show people how a change was made                     | The pull request's [session](/guides/why-blame/#sessions)                                                       |
| See who is working on what, and not collide           | [Claims and dependencies](/work/claims-and-dependencies/)                                                       |
| Script anything else                                  | The [REST API](/reference/api/), which has the same operations as the tools                                     |

The agent runs where you run it: on your machine, in your CI, or on a
[runner](/guides/self-hosted-runners/) of your own, on your own model
account. g1t runs no agents of its own; it keeps the code, the work items
and pull requests, the checks and the record of what happened. To start
one from g1t instead, see [hand a work item to g1t](#hand-a-work-item-to-g1t).

## Connect your AI client

Choose your client below. The repository pages and these docs remember your choice.
When you open a repository, the workspace's first configured AI provider supplies the
default; your explicit choice takes priority. OpenAI defaults to Codex, Anthropic
to Claude Code, Gemini to Gemini CLI, xAI to Grok, and self-hosted OpenAI-compatible
endpoints to Open WebUI. Other providers default to OpenCode. This only
chooses the instructions shown; it does not change your model or share your API key.

Claude Code's plugin records sessions through hooks. Codex can use the
[Codex plugin](#codex-marketplace), or connect directly with the commands below.
ChatGPT and other MCP clients connect through the same server.

### Chat apps and open-weight models

The connection belongs to the **chat client**, while the model supplies its
answers. For example, Open WebUI or LibreChat can connect g1t's tools to a
compatible model you host. An Ollama or vLLM model endpoint alone is not an MCP
client: configure the model in your chat app and add g1t separately.
Use a model with reliable tool calling.

| Client                | Connection                                                                                                                                                                  |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Grok chat             | [Custom MCP connector](https://docs.x.ai/grok/connectors) at grok.com/connectors; sign in to g1t.                                                                           |
| Claude chat / Desktop | [Custom remote connector](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp); choose automatic OAuth client registration. |
| Open WebUI            | An admin adds an [MCP Streamable HTTP server](https://docs.openwebui.com/features/extensibility/mcp/) with OAuth 2.1.                                                       |
| LibreChat             | Add the [MCP server configuration](https://www.librechat.ai/docs/configuration/librechat_yaml/object_structure/mcp_servers) shown above; each user signs in.                |

These are setup instructions based on the clients' documented capabilities;
they are not an end-to-end certification of every model and client version.
A chat app can read and act through g1t's tools without having a local shell.
Using Grok as g1t's configured AI provider is separate from connecting Grok chat
to your repositories. The same distinction applies to GPT and open-weight models.

Signing in opens g1t in your browser. The page lists what the agent will be
able to do; untick anything you would rather it could not, and approve.
There is no token to copy. An agent that asks for nothing in particular gets
the [Agent preset](/guides/authentication/#presets), which never includes an
admin scope. It shows up in
[Settings → Connected applications](https://g1t.sh/settings/applications),
where you can change what it may do, or sign it out.

A coding agent that pushes changes also needs git access. Where the [g1t CLI](/guides/cli/)
is signed in, `g1t auth setup-git` makes git use the same sign-in.
Otherwise git asks for a username and a password: use your g1t username
and an [access token](/guides/authentication/#access-tokens) with
`code:write`.

Ask it to list the open work items of a workspace or a repository, or to
work on one, and it
will use g1t's tools. It sees only the tools and actions its access allows.

### What to give an agent

Give an agent the least that lets it do its work:

| Choose  | For an agent                                                                                                                                                                                     |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Scopes  | The **Agent** [preset](/guides/authentication/#presets), which reads across g1t and writes what an agent's work needs, and never includes an admin scope. Add one only for a task that needs it. |
| Expires | The shortest that fits the work, such as 30 days.                                                                                                                                                |

A token reaches every workspace and repository you can. To keep an agent
to one workspace, give it that workspace's own
[workspace token](/guides/workspaces/#workspace-access-tokens) instead.

The same choices are on the sign-in page for an agent that connects with
OAuth, and in [Settings → Access tokens](https://g1t.sh/settings/tokens)
for a token. A call the agent's access does not allow is refused with the
scope it needs; see [scopes](/guides/authentication/#scopes). Everything
the agent does is done as you, and shows as you in the
[audit log](/guides/audit-log/).

## How an agent works on a work item

1. `work_item` with `work`, to load everything about it in one call: what
   done means, the repositories it is meant to land in and which have,
   who has claimed it, the pull requests already made for it, and what it
   is blocked by. Then `work_item` with `claim`, which also says who else
   is on it.
2. `pull_request` with `create` in the repository the change is for, and
   the work item's number as `item`. This opens a draft pull request and returns the git remote of its [working copy](/concepts/forks/#working-copies-for-pull-requests).
3. Clone the working copy, make changes, commit and push.
4. `pull_request` with `record_session` as it goes, so people can see its
   reasoning.
5. `pull_request` with `get`, to check `overlaps`, `behind` and the checks.
6. `pull_request` with `ready` and a summary of what changed and why.

### Work with no work item yet

Most of what an agent is asked starts without a work item, and a question,
a look around or a trivial fix never needs one. Record the session
anyway (`session` with `start`), with a `title` saying what it is for: the
team sees it in **Live now** on the repository's overview, under its pull
request or branch, and on the workspace's
[Sessions](/work/sessions/). When the work becomes a change others
should know about (a branch to push, a pull request), look for its work
item (`work_item` with `list` or `list_claims`) and claim it. If there is
none, `work_item` with `claim`, a `title` and no `number` opens one, with
the repository as its origin, and claims it in one step, and attaches the
session (`session_id`) to it:

```json
{
  "name": "work_item",
  "arguments": {
    "action": "claim",
    "repo": "flagon-io/hello",
    "title": "Preview builds time out on large repositories",
    "session_id": "ses_01m4b2c3d4e5f6g7h8j9k0m1n2"
  }
}
```

See [Work with no work item yet](/guides/sessions/#work-with-no-work-item-yet).

The call that starts the pull request:

```json
{ "name": "pull_request", "arguments": { "action": "create", "repo": "flagon-io/hello", "item": 42, "agent": "claude-code" } }
```

`agent` names the harness, so people can see what made the change. Its
commits show with the agent's name and mark too, from the address the
agent writes on them.

Every push runs the repository's [workflows](/guides/actions/#checks) on
the pull request, as for anyone's. `pull_request` with `get` returns its
`statuses` and `required_checks`, the checks the default branch requires
before it merges. When one fails, `workflow` with `get_run` and `job_logs`
says why; push a fix and the workflows run again. Run the same tests and
linters the workflows run before you push, and you will rarely need to.

When `main` has moved, `pull_request` with `update_branch` brings the pull
request up to date in a few seconds. When the changes clash, pull `main`
into the working copy, resolve and push. The pull request can then be
merged, or joins the [merge queue](/guides/merge-queue/) when the
repository uses one.

When the merge queue takes an agent's pull request out because it fails
combined with the pull requests ahead of it, g1t
[says which ones and which check failed](/guides/merge-queue/#who-is-told):
in the pull request's session, as an `integration_failure` decision
(`pull_request` `list_decisions`, and `work_item` `decisions` for its
work item), and as the `integration.failed` event.
The agent reads the other pull request's changes, fixes its own, and
pushes; once the checks pass, the pull request rejoins the queue by
itself. It can say what it changed with `pull_request` `record_decision`
(`kind` `fix`), and `repository` `why` explains any line it is unsure of.

### Repository instructions

Each agent reads a repository's instructions from a file at its root:
Claude Code from `CLAUDE.md`, and Codex, OpenCode and Cursor from
`AGENTS.md`. To keep one file, write `AGENTS.md` and put `@AGENTS.md` in
`CLAUDE.md`. A few lines there make every agent work the same way on g1t:

```md title="AGENTS.md"
## Working on g1t

- Work in a draft pull request (`pull_request` `create` with the work
  item as `item`),
  and record your session with `record_session` before each push.
- Read `overlaps` and `behind` on `pull_request` `get` before going far.
- Say why you made a choice with `pull_request` `record_decision`.
```

An agent with a shell can use the [g1t CLI](/guides/cli/) instead of the
tools, and claim the work item, record its session and hand off with it: the
lines for that are in
[other coding agents](/guides/claude-code-plugin/#other-coding-agents).
With Claude Code, the [plugin](/guides/claude-code-plugin/) does this for
you.

## Record the session

A pull request's session is the record of how it was made: the prompts,
the agent's reasoning, the tools it ran and what they returned. People read
it on the pull request's **Session** tab, and
[why-blame](/guides/why-blame/) uses it to explain each line.

An agent can record its own session with the `pull_request` tool's
`record_session` action. It takes a list of `entries`, each with a `kind`
(`prompt`, `message`, `tool_call`, `tool_result` or `note`) and `text`,
and tool entries also carry the `tool` name. Record before each push: an
entry is tied to the commit that was the head when it was recorded. Do not
put secrets in a session: g1t takes out what looks like a credential, and
shows what a session recorded only to the workspace's members (a prompt
only to whoever typed it), but that is a safety net. See
[Who sees what](/work/sessions/#who-sees-what).

### Recording sessions automatically

With Claude Code, install g1t's plugin and every session in a g1t
repository is recorded without the agent having to remember:

```sh
claude plugin marketplace add https://g1t.sh/flagon-io/g1t-plugins.git
claude plugin install g1t@g1t
```

Its hooks record your prompts, the tools Claude uses and what it called
them with, and its pushes, through the [g1t CLI](/guides/cli/), which
must be installed and signed in (`g1t auth login`), and title each
session with what its first prompt asked for. They never send what a
tool returned. The plugin also gives Claude the work item's context when
a session starts (or, with no work item, when to claim or open one), g1t's
MCP server, and commands to claim and hand off work items. See [Claude Code plugin](/guides/claude-code-plugin/) for
everything it records, and how to opt out.

Other agents record a session with the same CLI commands, from their
instructions file: see
[other coding agents](/guides/claude-code-plugin/#other-coding-agents).

## Staying out of each other's way

Several agents, and people, can work on one repository at once.
`pull_request` with `get` returns:

- `overlaps`: other pull requests in progress that change files this one
  changes, with the paths. An overlap with a pull request for a different
  work item will become a conflict for whichever merges second, so narrow the
  change, or say so in the pull request.
- `behind`: whether `main` has moved since the pull request was made. If
  it has, `update_branch` before asking for a merge.

Required checks, [rules](/guides/rules/) and the
[merge queue](/guides/merge-queue/) hold for an agent's pull request
exactly as for a person's.

## Hand a work item to g1t

g1t runs no model of its own, but it can start a session for you on the
workspace's own Anthropic account. Once an owner adds an Anthropic key
under [**AI**](/guides/ai/):

- **Assign to g1t** in a work item's sidebar (or `g1t work edit 12
--add-assignee g1t`), or mention `@g1t` in a comment on a work item or
  pull request, with what you want done.
- **Start a session** on a work item's page, `g1t work dispatch 12`, or the
  `session` tool's `dispatch` action, to choose the mode (`plan`,
  `implement` or `review`).

g1t reacts 👀, then starts the session as you, with a token for that
repository only that is revoked when the session ends. It installs the
g1t CLI, clones the repository and works the way this page describes; its
card shows in the work item's conversation, and Anthropic bills the account
for it. Without an Anthropic key, `g1t work dispatch` prints a Claude Code
command to run yourself instead. See
[Assign g1t](/guides/sessions/#assign-g1t-or-ask-it-in-the-thread) and
[Start a session on your Anthropic account](/guides/sessions/#start-a-session-on-your-anthropic-account).

## Start an agent when something happens

To run your agent without anyone starting it by hand, react to g1t's
events:

- **Webhooks.** Register an address for a repository or a whole workspace
  with the `webhook` tool or in its settings, and choose the events, such
  as `work_item.labeled`, `work_item.assigned`, `comment.created`,
  `checks.completed` or `workflow.completed`. Each delivery is signed. See
  [webhooks](/guides/webhooks/).
- **Workflows.** A workflow in `.g1t/workflows/` can start on `work_item` or
  `work_item_comment` and run your agent's command line on a g1t runner, with
  its key in a [secret](/guides/secrets-and-variables/). See
  [GitHub Actions](/guides/actions/).
- **Notifications.** An agent that works as you can read your inbox with
  the `notifications` tool: review requests, mentions, assignments and
  your work's checks, each with why you were told.

## Reviewing as an agent

An agent can review as well as write. Given a work item with several pull
requests, it can call `pull_request` with `changes` and `read_session` on
each, compare them, and read each one's check results from `get`. It can
leave findings on specific lines with `work_item` and `comment`, give a verdict
with `pull_request` and `review`, and, with the Write role, `merge` the
best one. It cannot approve or request changes on a pull request it opened.

## Artifacts

Your agent can read and write a workspace's artifacts: its docs, and later
its slides, designs and dashboards. The `artifact` tool does it as you,
so it opens only what you can open, and changes only what you can change.
Its token needs `artifacts:read` to read them (the Read only and Agent
[presets](/guides/authentication/#presets) have it), `artifacts:write` to
make and change them, and `artifacts:admin` to share them or delete them
for good. A token without one of these sees no `artifact` tool, and a
token sees only the actions its scope allows.

1. Find what is there with `list` (narrow with `kind`, `space` or `q`) or
   `search`, which matches words and meaning and returns the passage that
   matched.
2. Read one with `read`. A doc comes back as Markdown in `content`, with
   its top-level `blocks` and their ids, and `can` says whether you may
   edit it or only suggest.
3. Change it with `edit`: `markdown` and a `target`, which is `append`,
   `document` (replace it all), a `section` by its `heading`, or `blocks`
   from one block id to another. With the edit role the change is made, as
   a new version; with the comment role, or with `suggest_only`, it is
   filed as a suggestion that the doc's editors accept or reject.
4. Make one with `create`. Left out `space` and `parent_id`, it lands in
   your Private, where only you can open it until you share it.

```json
{
  "action": "edit",
  "workspace": "acme",
  "artifact_id": "fol_01kq7c4e6g8j0m2p4r6t8v0x2z",
  "target": { "kind": "section", "heading": "Risks" },
  "markdown": "## Risks\n\nThe migration needs a maintenance window.\n",
  "note": "Adds the migration risk"
}
```

Name an artifact by its id (`fol_…`) or by its link. Each action is also
a REST route under `/workspaces/{workspace}/artifacts`; see the
[API reference](/reference/api/). These are not workflow runs' artifacts,
which are the `workflow` tool's. Slides, designs and dashboards answer
that they are not here yet. A workspace's own token cannot use artifacts:
they always belong to a person.

## Filing work items from another system

Anything that holds an access token can open work items: an error
tracker, a monitor, a script. Call the `work_item` tool with `create`, or
`POST /workspaces/{workspace}/work`, with a title, a description, labels
such as `bug`, and the `repo` it is about as its origin. Its token needs
`work:write`. The work item is attributed to the account the token
belongs to.

## Tools

Each tool is a kind of thing on g1t and takes an `action`, such as `get`
or `create`. Repositories are given as `owner/name`, pull requests as the
repository and a `number`, and work items as the `workspace` and a
`number`.

| Tool            | What it covers                                                                                                   |
| --------------- | ---------------------------------------------------------------------------------------------------------------- |
| `search`        | Code, repositories, work items, pull requests and people across g1t; a tracker's ticket                          |
| `repository`    | Repositories, their settings, rulesets, branches and releases                                                    |
| `work_item`     | Work items, their repositories, labels and comments; a work item's whole context, and claims                     |
| `pull_request`  | Pull requests: create, record and read sessions, review, merge, the merge queue                                  |
| `session`       | Your harness's session: start, update, record, end, get, list; dispatch work on a work item; who else is working |
| `workflow`      | Workflow runs and logs, checks, deployments, environments and runners                                            |
| `observability` | A repository's requests, logs, traces, errors and metrics in production                                          |
| `package`       | Packages in every registry                                                                                       |
| `secret`        | Secrets and variables                                                                                            |
| `security`      | Secret scanning, code scanning, vulnerable dependencies and advisories                                           |
| `webhook`       | Webhooks and their deliveries                                                                                    |
| `access`        | Who has which role on a repository, and deploy keys                                                              |
| `team`          | Teams and their members and repositories                                                                         |
| `workspace`     | Workspaces, members, labels, milestones, integrations, repositories, rulesets and token rules                    |
| `ai`            | The workspace's AI providers, and what Ask answers with                                                          |
| `billing`       | Usage, budget and invoices                                                                                       |
| `notifications` | Your inbox                                                                                                       |
| `account`       | Who the token acts as, and your invitations                                                                      |
| `artifact`      | A workspace's docs                                                                                               |

[MCP tools](/reference/mcp/) lists every action with its required inputs,
its scope and its REST route.

## Other clients

The server speaks MCP over streamable HTTP and answers each request with
JSON. Every call needs to be signed in. Opening
[mcp.g1t.sh](https://mcp.g1t.sh) in a browser shows what the server is, how
to connect, and the tools it offers.

A client that supports MCP authorization needs only the URL. An
unauthenticated request is answered with `401` and a pointer to
`https://mcp.g1t.sh/.well-known/oauth-protected-resource`, from which the
client finds g1t's authorization server, registers itself, and sends you to
your browser. A client that asks for scopes sends them in `scope` on the
authorization request. See
[signing in with OAuth](/guides/authentication/#signing-in-with-oauth).

A client that does not can send `Authorization: Bearer <token>` with an
access token.

## Codex marketplace

Add g1t's small plugin marketplace:

```sh
codex plugin marketplace add https://g1t.sh/flagon-io/g1t-plugins.git
codex plugin add g1t@g1t
```

In the ChatGPT desktop app's Plugins directory, select the **g1t** marketplace,
install **g1t**, and authorize its MCP connection. Restart the app if the source
has not appeared. The plugin bundles the MCP server and a skill for working on
g1t work items and recording sessions. It does not install Claude Code's hooks.
If you already added the standalone `g1t` MCP server, disable that duplicate
connection when using the plugin.

The direct Codex MCP commands above work without a marketplace. ChatGPT's
**Add custom MCP server** flow is also available independently; a Git marketplace
is not a listing in OpenAI's public plugin directory.
