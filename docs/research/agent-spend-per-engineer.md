# Agent spend and agent work per engineer

Research, 2026-10-18. The question: how g1t should show agent spend and agent work per engineer, across every coding agent a team uses, as well as or better than the products that already do it.

Sources are vendor docs, API references and changelogs, linked inline. **UNCONFIRMED** marks a claim that rests on a secondary source, on vendor source code without docs, or on nothing I could open. Vendor marketing claims are labelled as such.

## Where g1t stands

These are the integration points the plan below changes.

**Claude Code** is the only agent that reports spend.

- `plugins/claude-code/hooks/g1t.mjs` reads `message.usage` from the transcript on `Stop`, `SubagentStop` and `SessionEnd`, and removes duplicates by message id plus `requestId`.
- It sends the totals with `g1t session heartbeat --usage-json` (CLI 0.4.1 or later).
- That becomes `PATCH /repos/{owner}/{name}/sessions/{id}`, then the work service's `update_session`.
- The work service prices it with `crates/contracts/src/model_prices.rs`, which has Anthropic list prices only, and writes `sessions.usage` and `sessions.cost_usd` (`services/work/migrations/0053_session_cost.sql`).

**Other agents** report no cost.

- Codex (`plugins/codex`) has no hooks.
- Other agents use `plugins/other-harnesses/AGENTS.snippet.md`, manual CLI calls without usage.
- Even if they sent tokens, `model_prices.rs` would price a non-Anthropic model as unknown (`cost_partial`).

**Provider reports**, in `services/billing/src/provider_costs.rs`:

- Anthropic `cost_report` is grouped by `workspace_id` and `description`.
- OpenAI `organization/costs` is grouped by `line_item` and `project_id`.
- Neither is grouped by user. Both are stored in `provider_costs` for the whole organization.

**How work is attributed** (`services/work/src/signals/base.sql`, `weeks.sql`, `pulls.sql`):

- A pull request is an agent's when its `pulls.agent` is `agent`, its author is the g1t agent, or a session is tied to it through `session_links`, `sessions.pull`, or a branch touch.
- A session's cost is split evenly across the pull requests it is tied to.
- Direct pushes count only as `agent_commits`, built from the plugin's `session touch` reports.

**Why a solo workspace sees almost nothing** (`apps/web/app/lib/signals.ts`):

| Finding | Why it stays hidden for flagon-io                                                                             |
| ------- | ------------------------------------------------------------------------------------------------------------- |
| spend   | `quarterSpend` counts only per-pull cost, so direct-push sessions drop out. It also needs two or more groups. |
| review  | Needs a non-owner review.                                                                                     |
| shipped | Needs a closed milestone.                                                                                     |
| stalled | Needs open pull requests.                                                                                     |
| rework  | Needs 5 or more agent merges a week.                                                                          |
| silos   | Needs 3 people.                                                                                               |
| spread  | Needs 2 people who adopted a harness later.                                                                   |

The pulse tiles do count direct-push spend (`signals.server.ts:140`).

**Who can see what:**

- There is no per-person spend view. Billing `Usage` has no actor dimension (`crates/contracts/src/billing.rs:311`).
- Session visibility is own, member or outside (`services/work/src/coordination/shown.rs`). Members see each other's `cost_usd`, but not each other's prompts.

**Open question.** The sessions this research ran, including its own subagents, came back from coordination with `cost_usd: null` after they ended. Either the coordination payload leaves cost out, or subagent usage doesn't arrive. Step 0 checks which.

**How agents mark their own commits:**

- **Copilot coding agent:** Copilot is the commit author, the assigning person is co-author, and an `Agent-Logs-Url` trailer links the session. [changelog](https://github.blog/changelog/2026-03-20-trace-any-copilot-coding-agent-commit-to-its-session-logs)
- **Cursor:** the CLI adds a `Made with Cursor` trailer. Cloud agents commit as "Cursor Agent" with the person as `Co-authored-by`. [docs](https://cursor.com/docs/cli/reference/configuration)
- **Devin:** the author is configurable: Devin, co-authored, or the person.
- **Claude Code:** `Co-Authored-By: Claude`.

**What "cost" means differs by plan.**

- On a subscription (Claude Max, ChatGPT plans, Cursor seats), every token-based figure is a list-price **estimate**: what the work would cost through the API, not what was paid.
- Swarmia calls this "token value". LinearB's docs say "Estimated consumption is not a billing total."
- g1t should say so too. The Claude Code Analytics API's `customer_type` (`api` or `subscription`) tells the two cases apart.

### Solo developers and small teams

What these tools have in common is that they're about **limits, not ROI**:

- **Claude Code `/usage`:** session cost, per-model tokens, a cache-hit line, plan-limit bars, and which skills, subagents and MCP servers used the most. `--max-budget-usd` caps a run. Anthropic's benchmark is about $13 per developer per active day. [docs](https://code.claude.com/docs/en/costs)
- **ccusage:** daily, weekly, monthly and per-session reports, plus five-hour `blocks` with burn rate and a projection against the plan window. Covers Codex, Amp, Copilot CLI and Gemini CLI from their local files. [repo](https://github.com/ryoppippi/ccusage)
- **tokscale, Sniffly, Grafana stacks** (claude-code-otel and others): top sessions by cost, cost by model, clusters of errors.
- **Langfuse:** traces from Claude Code and Codex Stop hooks and from Copilot's OTel; cost per developer, project and session. [docs](https://langfuse.com/resources/engineering/coding-agent-tracing)
- **Git AI:** agent hooks write per-line authorship to `refs/notes/ai` (agent, model, session); the paid tier adds cost per PR. [docs](https://usegitai.com/docs/get-started/how-git-ai-works)

**The gap:** almost no small-team tool connects spend to **work that landed**. They answer "how fast am I burning?", not "what did that buy, and what was thrown away?".

## 2. Patterns worth copying

1. **Three paths in, one number out.** Every vendor joins vendor APIs (daily, backfilled, per user), OTel (real time, any provider) and git. g1t has a fourth path, its own session record, which the others lack.
2. **Call it an estimate and show the basis.** Show "list-price value" next to the actual invoice when a provider report exists. Use `customer_type` and plan to say which case applies.
3. **Detection in tiers, with the rule shown** (Swarmia). For every change g1t calls an agent's, say why: a session trailer, a session tie, a co-author, the Copilot author, or a `Made with Cursor` trailer.
4. **Cloud-agent work belongs to the person who started it** (DX, Swarmia, Devin's `user_id`, Copilot's co-author).
5. **Spend split over work by effort** (Swarmia). Use it only where g1t lacks a direct link, and label it as a split.
6. **Idle-seat and plan-fit checks first** (Swarmia, Cursor): token value against what the seat costs.
7. **Self-view softens individual data** (Span, Cursor members, DX's AI % override, Devin Personal Analytics).
8. **Compare only with your own history** (RadiantOps). This is also the only baseline that works for one person.
9. **A daily digest that says what to act on** (RadiantOps Signal, Waydev and Swarmia assistants). g1t already has one: Home.
10. **For solo users, lead with limits:** burn rate, cache efficiency, and which skill, subagent or MCP server is eating budget.

## 3. What g1t can do that they can't

The products above infer the link between spend and work from outside. g1t is the forge and records the sessions, so it has the link directly:

- **An exact join, not a heuristic.**
  - A session's `G1t-Session` trailer ties its cost to the commit, the pull request, the work item it closes, and the merge-queue result.
  - Swarmia needs a 24-hour window, Cursor needs line signatures, and Span needs an ML model to approximate this.
- **Spend that never landed.** g1t sees sessions that cost money and produced no commit, sessions whose branch was abandoned, and pull requests closed unmerged. Only Span claims to see dead ends, and only through a recorder on each machine.
- **Direct pushes.** Products built on PR data miss them. g1t receives the push and reads its trailers (`services/work/src/coordination/pushed.rs`).
- **Rework from the history itself.** g1t sees follow-up commits and reverts on the same lines, failed checks and fix-ups in the merge queue, and their cost. It doesn't depend on a "rework" heuristic over someone else's API.
- **One identity.** The session actor, the git pusher and the reviewer are one g1t account, so there is no email-to-author mapping page. Provider APIs keyed by email (Anthropic, Cursor, Amp, Windsurf) map onto g1t users through their verified addresses.
- **The cost of reviewing agent work.** Review time, the number of rounds, and the CI minutes an agent's pull request used are all g1t's own data.
- **Every harness in one place.** Claude Code, Codex, Cursor, Copilot CLI, Gemini CLI and Devin all have hooks now with `session_id` and `transcript_path`, so one plugin pattern covers them. The products above each need vendor admin keys, and most of those need Enterprise plans.
- **Useful for one person.** Because g1t records sessions itself, a solo developer gets cost per landed change and spend that never landed without any admin API. No product above serves that case.

## 4. Privacy model

The stance: **spend is information about work, not a score for people.**

1. **Your own, in full.** Every engineer sees all of their own sessions, spend, prompts and what landed, on every harness. This matches what `Sight` already does for sessions.
2. **Others' spend appears as the cost of work, not ranked by person.**
   - Teammates see what a change, work item, milestone or team cost, and who worked on it, as today.
   - There is no view that lists or sorts people by spend, and no leaderboard, score or percentile.
3. **Per-person totals are a workspace setting.** "Spend by person" can be shown to:
   - **Owners and billing managers**, the default;
   - all members;
   - or nobody.

   It is for budgets and plan fit, and the page says so. Every person always sees their own.

4. **A minimum group of 3 for rollups.** A team or group total is shown only when it covers three people or more. Otherwise it would reveal a person's figure to people the setting doesn't allow. A one-person workspace is all self-view, so this never hides anything there.
5. **Provider data waits for consent.** Per-user rows from a provider API, such as an Anthropic Analytics email or a Cursor `userEmail`, are joined to a g1t user only through an address that person has verified. Unmatched rows stay in "not linked to anyone".
6. **Content stays with its author.** Prompts and tool output stay own-only for members (as today) and are never sent to an outside service.
   - g1t's own OTel receiver should drop `user_prompt`, `assistant_response` and body events unless the person turns them on.
   - Gemini CLI's `logPrompts`, which defaults to true, should be set to false in the settings g1t writes.
7. **Opting out is visible.** `G1T_RECORD=0` and `G1T_RECORD_PROMPTS=0` already exist. Totals show how much they leave uncounted ("3 sessions unrecorded"), so nobody mistakes missing data for zero.
8. **No outside benchmarks.** Compare only with the workspace's own history, as Home already does.
